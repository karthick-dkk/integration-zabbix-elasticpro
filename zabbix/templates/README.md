# ElasticPro templates (Zabbix 7.0)

The templates ElasticPro feeds. The first four are copied from the ElasticPro repository at v0.3.10
(`deploy/zabbix/template-*.yaml`, where they are generated by `tools/zabbix-*-template.mjs`
— that is the one place they are edited; this folder is a copy for a Zabbix that is set up
from this project alone).

| File | Template | Fed by |
|---|---|---|
| `template-elasticpro.yaml` | **ElasticPro automation** — the automation rules' verdicts per cluster, from the JSON document `tools/elasticpro-scrape.mjs` writes; one HTTP item, no agent | the automation scraper |
| `template-elasticpro-alerts.yaml` | **ElasticPro alerts** — every alert the Alerts page raises, as Zabbix problems | the automation scraper |
| `template-elasticpro-client-plan.yaml` | **ElasticPro client plan** — the volume report per cluster (the Volume widget's columns come from it) | the plan scraper |
| `template-elasticpro-log-delay.yaml` | **ElasticPro log delay** — the scheduled log-delay measurement | the core's delay sink |
| `template-elasticpro-request-gate.yaml` | **ElasticPro request gate by Zabbix trapper**: ElasticPro's own request gate (in flight, queued, wait p95, refusals, memory), from one trapper item | the core's push (`ZABBIX_METRICS_HOST`, ElasticPro 0.3.24+) |

Import: *Data collection → Templates → Import*, or `deploy/zabbix/setup/zbx_phase34.py` in the
ElasticPro repository, which imports all four in order. Then `master/import.py` here, then
*Write master template* on the Clients page.

## ElasticPro request gate by Zabbix trapper

Unlike the four above, this one is written here and this file is its source. The ElasticPro core
(0.3.24 or later) pushes one JSON value a minute to the trapper item `elasticpro.gate.raw` by the
Zabbix API's `history.push`, once `ZABBIX_METRICS_HOST` in its `config.txt` names the host this
template is linked to. Every other item is a dependent item of that one, read with JSONPath.
The value is aggregates only: no cluster name, address or URL.

Triggers:

| Trigger | Severity |
|---|---|
| request figures stopped arriving (`nodata`, `{$ELASTICPRO.GATE.NODATA}`) | Average |
| requests queueing at every push for the window | Warning, or Average past the crit macro (the warning depends on it) |
| requests turned away in the window | Warning / Average, the same way |
| a person's wait p95 above the threshold for the window (at least `{$ELASTICPRO.GATE.WAIT.SAMPLES}` minutes with requests, and people asking in the last minute, so it recovers when they stop) | Warning / Average |
| every request paused longer than `{$ELASTICPRO.GATE.PAUSED.MAX}` | Warning |
| in-flight answer memory above `{$ELASTICPRO.GATE.INFLIGHT.PUSED.WARN}`% for the window | Warning |
| answers over the response cap in the last hour | Info |
| version changed | Info, closed by hand |

After import:

1. Create a host (for example `ElasticPro`, in a host group of its own). It needs no interface,
   and the item's *Allowed hosts* stays empty. Link the template.
2. Let ElasticPro's paired token push. The pairing role *ElasticPro sync* allows `history.push`
   from this release on. An install paired before re-pairs once (ElasticPro: Config → Zabbix →
   Pair with Zabbix), which updates the role, or adds `history.push` to the role by hand. The role
   is of the Super admin type, so the paired token can then write to **any** trapper item in Zabbix,
   though it still cannot change configuration. To avoid that, remove `history.push` from the role
   and give the core a push-only token with read-write on this host's group only, as
   `ELASTICPRO_ZABBIX_METRICS_TOKEN_FILE` (ElasticPro's `deploy/README.md`, "The request figures in
   Zabbix").
3. Set `ZABBIX_METRICS_HOST=<host's technical name>` in ElasticPro's `config.txt` and run
   `deploy/deploy.sh --apply-config`.
4. Adjust the `{$ELASTICPRO.GATE.*}` macros on the host if the defaults do not suit.

## Moving existing hosts onto these templates

Hosts that run older Elasticsearch, Linux or earlier ElasticPro templates are moved with
`../tools/migrate-templates.py`, which keeps every stored value (it renames keys and lets the
link adopt the existing items rather than starting new ones). Step by step, prerequisites,
verification and rollback: [`../docs/MIGRATION.md`](../docs/MIGRATION.md).

## Testing

- `python3 ../tools/test/validate_template.py <file>` — static checks (references, uuids,
  credentials, macros). CI runs it on every template in this folder and on the templates the
  Clients page generates (`../tools/test/gen_templates.php`).
- `../tools/test/template_live_test.py` — imports a `ztest-` copy of each template into a test
  Zabbix (`ZABBIX_URL`, `ZABBIX_TOKEN`), proves the import is idempotent, sets every macro on a
  test host and feeds payloads (trapper values; `mock_scrape_server.py` for the automation
  template's HTTP item), including the edge cases: empty secret, wrong URL, thresholds at the
  boundary, stale data. `--dry-run` needs no Zabbix; `--fast` skips the staleness waits.

These files are copies. Two fixes made here (2026-10) must also reach the ElasticPro
repository, or the next copy brings the old versions back: the automation template's
"scrape has stopped running" trigger (`fuzzytime(...)=0 or nodata(...)=1`) in
`deploy/zabbix/template-elasticpro.yaml`, and the `template_groups` section that
`tools/zabbix-delay-template.mjs` should emit for the log-delay template.
